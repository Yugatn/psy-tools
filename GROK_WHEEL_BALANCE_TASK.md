# Задача для Grok: полное совершенствование Wheel of Balance

Репозиторий: https://github.com/Yugatn/psy-tools
Основной проект: `wheel/`

## Цель

Провести полноценный аудит и исправление существующего проекта «Колесо баланса».

**Новые колёса, новые сферы и новые смысловые разделы НЕ добавлять.**

Главный эталон функциональности — текущее основное колесо:

`wheel/index.html`

Все существующие детальные колёса должны иметь тот же пользовательский опыт и тот же набор функций, адаптированный к конкретному детальному уровню.

## Критически важное требование

Детальное колесо — это не упрощённая версия основного колеса.

Оно должно быть функциональным эквивалентом основного колеса:

- тот же интерфейс;
- та же логика оценки;
- та же шкала 0–10;
- тот же прогресс;
- та же отрисовка колеса;
- те же лучи;
- те же результаты;
- история и динамика;
- цели и план улучшений;
- журнал;
- рефлексия;
- календарь;
- напоминания/возврат к намерению, если функция уже присутствует в основном колесе;
- экспорт/импорт;
- поделиться результатом;
- сброс;
- зона внимания;
- переходы между уровнями;
- адаптивность;
- Telegram WebApp-функции, если они используются основным колесом.

При этом данные каждого детального колеса должны быть изолированы собственным стабильным ключом localStorage.

## Что проверить

### 1. Все существующие колёса

Проверить:

- `wheel/index.html`
- `wheel/health/index.html`
- `wheel/work/index.html`
- `wheel/finance/index.html`
- `wheel/relationships/index.html`
- `wheel/social/index.html`
- `wheel/development/index.html`
- `wheel/rest/index.html`
- `wheel/creativity/index.html`
- `wheel/self_awareness/index.html`
- `wheel/detail/index.html`

Не создавать новые колёса.

### 2. Детальная навигация

Исправить все случаи, когда:

- открывается последняя страница вместо выбранного луча;
- теряется `parent`;
- теряется `ray`;
- теряется `label`;
- ломается `trail`;
- кнопка «Назад» ведёт не на исходное колесо;
- URL содержит двойное кодирование;
- после возврата восстанавливается неправильный scroll;
- детальный уровень открывается с данными другого уровня.

Использовать стабильную структуру параметров:

`parent`, `ray`, `label`, `trail`, `back`.

### 3. Первое открытие

Новое детальное колесо не должно выглядеть заполненным.

Не использовать фиктивные оценки `5` как сохранённое состояние.

До оценки пользователь должен видеть пустое/неоценённое состояние.

После первой оценки значение сохраняется.

Существующие реальные сохранённые оценки пользователя не удалять.

### 4. Лучи

На каждом колесе должны быть видимы:

- центр;
- круги шкалы 0–10;
- радиальные лучи;
- названия лучей;
- текущие значения;
- визуальное заполнение;
- интерактивные точки/маркеры, если они предусмотрены основной версией.

Проверить canvas на desktop и mobile.

### 5. Полный паритет функций

Сравнить основной и детальный HTML не только визуально, но и программно.

Составить список:

- DOM id;
- функций JavaScript;
- localStorage keys;
- обработчиков событий;
- модальных окон;
- кнопок;
- секций результата.

Все функции основного колеса, которые имеют смысл для детального уровня, должны работать и там.

Если функция зависит от контекста, адаптировать её, а не удалять.

### 6. Данные

Для каждого детального уровня создать детерминированный storage namespace.

Пример:

`detailWheel:v3:<parent>:<trail>`

Нельзя смешивать:

- данные основного колеса;
- данные разных сфер;
- данные разных уровней одной сферы.

Добавить безопасную обработку повреждённых или старых localStorage-данных.

Не удалять старые данные без миграции.

### 7. История и динамика

История должна хранить:

- дату/время;
- значения всех лучей;
- цели;
- данные улучшений;
- необходимые пользовательские заметки.

Экран динамики должен показывать:

- изменение каждой сферы по датам;
- было / стало;
- изменение в абсолютных значениях;
- прогресс к цели;
- достижение цели;
- переход из элемента динамики непосредственно к соответствующему колесу.

Для детального колеса использовать его собственную историю.

### 8. Цели и улучшения

Сохранить существующую механику основного колеса:

- целевое значение;
- срок;
- конкретный следующий шаг;
- заметка;
- ожидаемый результат;
- последствия;
- прогресс;
- редактирование;
- удаление.

Не превращать это в декоративный блок.

### 9. Журнал

Проверить:

- сохранение;
- загрузку записи;
- удаление;
- дату;
- значения;
- заметки;
- совместимость с детальными ключами.

### 10. Экспорт / импорт

Проверить JSON:

- импорт не ломает структуру;
- значения ограничиваются 0–10;
- импорт не смешивает разные колёса;
- старый формат обрабатывается безопасно;
- экспорт содержит идентификатор колеса и уровень детализации.

### 11. Сброс

«Сбросить оценки» должен:

- сбрасывать только текущее колесо;
- не затрагивать родительское;
- не затрагивать соседние детальные колёса;
- очищать связанные цели/улучшения только после явного подтверждения;
- не уничтожать глобальные настройки.

### 12. Зона внимания

«Зона внимания» должна работать одинаково:

- определять минимальную оценку;
- показывать соответствующий луч;
- переводить пользователя непосредственно к нему;
- корректно работать при неполном заполнении.

Не считать неоценённые значения равными нулю без явного отображения этого состояния.

### 13. Безопасность данных

Проверить:

- `escapeHtml`;
- безопасный вывод пользовательского текста;
- отсутствие XSS через journal/reflection/goal/import;
- корректную обработку JSON;
- отсутствие падения страницы из-за повреждённого localStorage.

### 14. Производительность

Не допускать:

- бесконечных requestAnimationFrame;
- повторной регистрации обработчиков;
- лишних перерисовок canvas;
- деградации mobile;
- переполнения localStorage.

### 15. Совместимость

Проверить:

- desktop Chrome;
- Safari;
- мобильный Safari;
- Android Chrome;
- Telegram WebApp.

Не добавлять внешние библиотеки без необходимости.

Проект должен оставаться работоспособным как статический GitHub Pages сайт.

## Принцип архитектуры

Не дублировать логику бесконтрольно.

Если возможно, вынести общие функции в общий JS-модуль:

- wheel engine;
- storage;
- history;
- navigation;
- rendering;
- goals/improvements;
- journal;
- export/import.

Но существующую рабочую функциональность не ломать ради рефакторинга.
